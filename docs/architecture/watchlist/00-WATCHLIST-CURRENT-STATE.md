# Watchlist Current State

## Audit conclusion

`WATCHLIST_ARCHITECTURE: CREATE_NEW_SERVICE`

The current Wishlist implementation is a legacy `cinemaAI` monolith capability. It is not implemented in `catalog-service` or `booking-service`, and the API Gateway has no route target for the monolith. Adding the path to an existing microservice route would therefore produce a false exposure that still returns a downstream 404.

## Current contract

Base path: `/api/v1/wishlist`

| Method | Path | Behavior | Success |
|---|---|---|---|
| GET | `/api/v1/wishlist` | List the current user's saved movies | `200`, `ApiResponse<List<WishlistResponse>>` |
| POST | `/api/v1/wishlist` | Add a movie to the current user's list | `201`, `ApiResponse<WishlistResponse>` |
| DELETE | `/api/v1/wishlist/{movieId}` | Remove a movie from the current user's list | `204`, empty body |

Add request: `WishlistCreateRequest { Long movieId }`, with `@NotNull` validation.

Response: `WishlistResponse { id, movieId, movieTitle, posterUrl, createdAt }`.

The list is not paginated.

## Exact dependencies

### Persistence

`Wishlist` is a JPA entity with:

- `id` generated by the database;
- mandatory `ManyToOne` to legacy `User` through `user_id`;
- mandatory `ManyToOne` to legacy `Movie` through `movie_id`;
- inherited timestamps from `BaseEntity`;
- indexes on `user_id` and `movie_id`.

`WishlistRepository` provides:

- `findByUser(User)`;
- `findByUserAndMovie(User, Movie)`;
- `existsByUserAndMovie(User, Movie)`;
- `countByMovie(Movie)`;
- `deleteByUserAndMovie(User, Movie)`.

The database migration creates `dbo.wishlists` with foreign keys to `dbo.users` and `dbo.movies`, indexes, and a unique `(user_id, movie_id)` constraint. The current source also contains PostgreSQL-style migration files elsewhere in the monolith; the authoritative live schema/migration history must be reconciled before data migration.

### User identity

The controller receives `AuthenticatedUser` from the monolith JWT filter and passes `currentUser.getUsername()`, which is the user's email, into the service. The service then performs a database lookup through `UserRepository.findByEmail` and uses the resulting legacy `User` entity.

This is email-based application lookup, with a relational foreign key to the legacy user primary key.

### Movie identity

The add/remove request uses the legacy `Movie` primary key as `movieId`. The service resolves it through `MovieRepository.findById`. The response dereferences the entity to return title and poster URL.

The legacy `Movie` entity owns rich catalog fields including title, poster, release dates, status, approval/publication state, and cast metadata. Wishlist persistence currently depends on the same database and ORM entity graph.

### Security

The monolith `SecurityConfig` permits only selected public GET/POST paths. Wishlist is not public and falls through to `.anyRequest().authenticated()`.

The monolith uses:

- stateless Spring Security;
- `JwtAuthenticationFilter`;
- `AuthenticatedUser` principal;
- role/activation checks through the principal's authorities and enabled state.

### Errors

- Missing/invalid request body: `400`.
- Missing movie or wishlist item: `404` via `NotFoundException`.
- Duplicate add: `409` via `ConflictException`.
- Missing authentication: existing security behavior, normally `401`.
- Unexpected failures: `500` through `GlobalExceptionHandler`.

## Current Gateway state

`cinema-services/api-gateway/src/main/resources/application.properties` currently routes to:

- identity service;
- catalog service;
- booking service;
- payment service;
- recommendation service.

There is no `WISHLIST_SERVICE_URI`, no `cinemaAI` URI, and no `/api/v1/wishlist` predicate. `booking-service` and `catalog-service` source trees contain no Wishlist controller or Wishlist service.

## Architectural implication

The legacy implementation is functionally complete but not independently deployable in the current microservice topology. It also couples the wishlist table to both legacy user and legacy movie tables, so it cannot be moved by changing only the Gateway predicate.
